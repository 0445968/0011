# R10 — unified task drafts and approved workflow roadmap

## Foundation patch

Task settings in the Tasks editor (responsibility, assignees, priority, tags and new tag colors, completion-review policy, phase, service reference, prerequisite and blocker owner) now join the existing recoverable private work-plan draft. Text, dates, times, milestone, status and archive retain the same draft behavior. Reverting settings to their saved values removes those settings from the draft. Save task scopes the entire operation to that task; Save all applies the combined work plan.

The bundle RPC locks and checks the project and affected sidecar revisions, invokes existing authorization and audit functions, and saves the canonical plan in one transaction. Any failure rolls back the entire bundle. New task identities and metadata are created within that transaction. Draft-only `edits` never enter the canonical task JSON. Sidecar revision conflicts offer a saved-versus-draft comparison and an explicit choice. A per-staff save receipt verifies a lost response without inferring metadata success from task text alone.

Changing responsibility no longer automatically enables completion review. Existing requirements are preserved. A review-required client completion initially routes to an In Review draft instead of trying to bypass its completion gate; final completion still requires the established authorization and review evidence. Only admins see manual In Review/Rejected choices. Generalized review submission/approval routing is the next patch, not delivered by this foundation.

Task settings pause while an explicit save is in flight; later text/date edits remain separate pending drafts. Comments, file uploads, private notes, project-level membership and independently audited subtasks retain their existing explicit operations and are not included in task-setting bundles in this patch.

Toolbar dropdowns use viewport positioning outside the scrolling row's clipping boundary. Task date columns show `10 Oct 2026 11:00PM` in one row, with an explicit Show timezone preference.

## Subsequent coordinated patches — approved scope

1. **Ownership, permissions, roles and task-change approvals.** Separate immutable creator, owning organization and responsible side. Staff may propose edits to their own tasks; assigned members may progress permitted work. Bivi admin accepts task creation/requirement changes. Team/project manager coordinates without inheriting admin override rights. Prepare yulda@execs.com as team/project manager; crafterkite@gmail.com remains admin and becomes project manager. Verify account identity before applying roles; prepare an invite link without sending email.
2. **Unified completion approvals.** Required Bivi and/or client stages, admin-selected order, verified project contacts, one designated decision maker per stage, Bivi final authority. Submission creates approval and In Review atomically. In Review and Rejected tabs appear first while populated. Admin manual state selections invoke approval actions; override shows outstanding reviewers and records a reason when bypassing pending/rejected approval.
3. **Versioned review and return.** Fixed submitted snapshots, editable recoverable drafts, comment required to submit a replacement or release review. Superseded reviews stop reminders; prior decisions do not approve changed work. Return to own team means In Progress and urgent; return to other organization means Rejected until resumed. Review comments enter task comments with attachments/links/contacts/assets; per-user unread indicators. Effective urgent priority preserves the chosen base priority and also applies to deadlines within 24 hours/overdue until resolved.
4. **Template scheduling.** Effort presets 5/15/30/45 minutes and whole hours, custom five-minute increments; 1–16-hour working days, actual weekdays selected for 1–7-day weeks, timezone and holidays. Task/milestone dependency graph, parallel work with resource capacity, waiting periods and review allowances. Generate dates from project start, admin preview before activation, preserve approved baseline versus actual/forecast. Eligible staff may start future phases early with confirmation and actual start recorded; prerequisite bypass requires admin. Private per-user planned start/goal dates in My Tasks never rewrite approved deadlines.
5. **Deadlines and extension approvals.** Phase dates define milestone/task calendar limits (latest deadline for multiple linked phases), while generated task due dates follow dependency estimates. Earlier task dates allowed; later dates require approved extension. Extension requests have a reason and proposed date, retain current deadline pending decision, and do not silently shift siblings/phase commitments. Completion remains possible after due date. Milestones auto-complete only after all required tasks and reviews complete; phases remain active while extended work is unfinished.
6. **Client review windows and schedule holds.** Configurable 24/48/72/custom elapsed or business-hour windows. Fixed or percentage reminders, quiet hours, digest and escalation. Viewed is not decided; reminders stop upon decision, withdrawal or supersession. Active + Waiting for client while the client's stage is pending; Bivi independent work remains available. Overdue review offers an admin-controlled hold. Deliberate holds allow discussion/files/drafts but require resume for published task work. Client acceptance clears waiting only when all client decisions resolve; it does not auto-resume deliberate holds.
7. **Resume and schedule decisions.** Show client-overdue time, hold duration and actual dependency impact separately. Admin keeps baseline dates, previews/accepts affected downstream shifts, or chooses a feasible target deadline. Preserve completed dates and unrelated work, avoid double-counting simultaneous delays, respect working calendars/capacity, never add waiting time to estimated effort. Resuming never resets an unresolved approval clock.

Assets/deliverable requirements and private personal to-do lists remain in the broader workspace expansion roadmap. Small UI requests stay bundled with substantive patches. Each production release follows the established checked PR workflow; preview does not provide the user's usable admin session.
